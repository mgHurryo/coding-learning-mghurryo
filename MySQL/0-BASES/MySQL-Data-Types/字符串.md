# MySQL 字符串类型

字符串类型用于存储文本、编码、名称、描述等字符数据。MySQL 常见字符串类型按使用场景可以分为定长字符串 `CHAR`、变长字符串 `VARCHAR`、长文本 `TEXT` 系列和二进制字符串 `BINARY` / `VARBINARY`。

## 类型范围

| 类型 | 最大长度 | 存储特点 | 备注 |
| :--- | :--- | :--- | :--- |
| `CHAR(M)` | 0 到 255 字符 | 定长，短值会补空格 | 固定长度编码、状态码、定长标识 |
| `VARCHAR(M)` | 0 到 65535 字节内 | 变长，额外 1 到 2 字节记录长度 | 用户名、标题、手机号、邮箱等常用字段 |
| `TINYTEXT` | 255 字节 | 很短文本 | 使用较少，通常可用 `VARCHAR` 替代 |
| `TEXT` | 65535 字节 | 长文本，通常不适合作为高频索引字段 | 文章正文、备注、描述 |
| `MEDIUMTEXT` | 16777215 字节 | 中大型文本 | 较长内容、富文本 |
| `LONGTEXT` | 4294967295 字节 | 超大文本 | 极大文档，使用前要评估存储和查询成本 |
| `BINARY(M)` | 0 到 255 字节 | 定长二进制 | 固定长度 hash、二进制标识 |
| `VARBINARY(M)` | 0 到 65535 字节内 | 变长二进制 | token、摘要、加密后字节 |

## 长度语义

`CHAR(M)` 和 `VARCHAR(M)` 中的 `M` 表示字符数，不是字节数。实际占用字节数会受字符集影响，例如 `utf8mb4` 中一个字符最多可能占 4 字节。

```sql
username VARCHAR(64),
phone VARCHAR(20),
status_code CHAR(2),
summary TEXT
```

选择长度时要根据业务边界设定，不要把所有字段都写成 `VARCHAR(255)`。长度越明确，约束越清晰，也更利于索引和数据质量控制。

## 字符集与排序规则

字符串比较、排序和唯一性会受字符集与排序规则影响。MySQL 8 常见选择是 `utf8mb4` 字符集，用于完整支持中文、emoji 和多语言文本。

```sql
name VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
```

排序规则会影响大小写、重音和字符等价判断。设计唯一键时要确认是否需要区分大小写，例如用户名、邮箱、编码字段可能有不同要求。

## 选型建议

- 固定长度且短的值：使用 `CHAR`，例如国家码、性别码、固定 hash 前缀。
- 长度变化明显的短文本：优先 `VARCHAR`。
- 大段正文、备注、富文本：使用 `TEXT` 系列，并避免频繁全字段查询。
- 二进制内容或 hash 字节：使用 `BINARY` / `VARBINARY`，不要强行转成普通字符串。
- 需要索引的字符串字段：尽量控制长度，必要时使用前缀索引或额外生成可索引字段。

## 常见错误

- 把所有文本字段都设计成 `VARCHAR(255)`，导致约束松散、索引成本变高。
- 用 `TEXT` 保存短字段，使默认值、索引和查询都变得不方便。
- 忽略字符集，导致中文、emoji 或跨系统导入时出现乱码。
- 在很长的字符串字段上直接建完整索引，导致索引过大或超过长度限制。
- 用字符串保存数字、时间或枚举，导致排序、过滤和校验都变差。
