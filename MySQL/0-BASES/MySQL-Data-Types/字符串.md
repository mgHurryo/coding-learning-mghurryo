# MySQL 字符串类型

MySQL 的字符串类型分为两条语义线:

- 非二进制字符串保存字符, 包括 `CHAR`、`VARCHAR` 和 `TEXT` 系列。它们有字符集和排序规则, 比较的是字符。
- 二进制字符串保存字节, 包括 `BINARY`、`VARBINARY` 和 `BLOB` 系列。它们没有字符集和排序规则, 比较的是字节。

先决定数据是“文本”还是“任意字节”, 再决定定长、变长和最大容量。把二进制摘要当文本、把自然语言当字节或把所有内容都写成 `VARCHAR(255)` 都会丢失约束信息。

## 类型总表

### 短字符串
| 类型 | 声明长度 | 长度单位 | 存储特点 | 典型用途 |
| :--- | :--- | :--- | :--- | :--- |
| `CHAR(M)` | `0 <= M <= 255` | 字符 | 定长语义, 不足部分以空格填充 | 国家码、真正固定长度的短代码 |
| `VARCHAR(M)` | 名义上 `0 <= M <= 65,535`, 有效上限受行大小和字符集约束 | 字符 | 变长, 另有 1 或 2 Byte 长度前缀 | 用户名、标题、邮箱、外部业务键 |
| `BINARY(M)` | `0 <= M <= 255` | 字节 | 定长, 不足部分以 `0x00` 填充 | SHA-256 摘要、固定 16 Byte UUID |
| `VARBINARY(M)` | 名义上 `0 <= M <= 65,535`, 有效上限受行大小约束 | 字节 | 变长, 另有 1 或 2 Byte 长度前缀 | 可变长度 token、密文、协议字段 |

`CHAR(M)` / `VARCHAR(M)` 的 `M` 是字符数, 不是字节数。`utf8mb4` 的一个字符最多占 4 Byte, 所以 `VARCHAR(16384)` 不能想当然地放进普通行中。`BINARY(M)` / `VARBINARY(M)` 的 `M` 则是字节数。

`CHAR` 和 `BINARY` 省略 `M` 时长度默认为 1, 但工程 DDL 应显式声明长度。`VARCHAR` 和 `VARBINARY` 必须给出 `M`。

`VARCHAR` / `VARBINARY` 的声明最大字节长度不超过 255 时使用 1 Byte 长度前缀, 更长时使用 2 Byte。对 `VARCHAR` 来说, 判断依据是该列在字符集下可能需要的最大字节数, 不是当前某一行的实际字符数。

值超过列上限时, 严格 SQL 模式通常报错; 非严格模式可能截断并产生警告。尾随空格还有类型相关的特殊规则。生产环境应启用严格模式, 并在应用层先校验长度。

### 大文本与大二进制对象

| 文本类型 | 二进制类型 | 最大长度 | 长度前缀 |
| :--- | :--- | :--- | :--- |
| `TINYTEXT` | `TINYBLOB` | 255 Byte | 1 Byte |
| `TEXT` | `BLOB` | 65,535 Byte | 2 Byte |
| `MEDIUMTEXT` | `MEDIUMBLOB` | 16,777,215 Byte | 3 Byte |
| `LONGTEXT` | `LONGBLOB` | 4,294,967,295 Byte | 4 Byte |

表中的上限是类型协议上限, 不是一次写入一定能达到的容量。实际还受到 `max_allowed_packet`、客户端内存、日志、复制、备份、磁盘和执行计划内存等限制。

`TEXT` 系列的上限以字节计算, 可保存的字符数取决于字符集。`LONGTEXT` 在 `utf8mb4` 下不能简单理解为可以保存 4,294,967,295 个字符。

## CHAR 与 VARCHAR

### 定长和变长不是唯一差异

`CHAR` 适合长度真正固定且很短的字段, 例如 ISO 3166-1 两位国家码。`VARCHAR` 适合长度变化明显的字段。

```sql
country_code CHAR(2) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
display_name VARCHAR(80) CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci NOT NULL
```

`CHAR` 会以空格补到声明长度。取值和比较中的尾随空格行为还受类型与 collation 的 `PAD_ATTRIBUTE` 影响, 因此不要让尾随空格承担业务含义。MySQL 8 的 Unicode 9.0 collations 通常是 `NO PAD`, 旧 collation 可能是 `PAD SPACE`; 应查询元数据而不是凭名称猜测。

```sql
SELECT COLLATION_NAME, PAD_ATTRIBUTE
FROM information_schema.COLLATIONS
WHERE COLLATION_NAME IN ('utf8mb4_0900_ai_ci', 'utf8mb4_general_ci');
```

`VARCHAR` 不会按声明长度补空格, 但比较结果仍由 collation 决定。唯一索引也使用同一比较语义, 所以大小写、重音或尾随空格是否被视为相同会直接影响能否插入。

### 字符数、字节数和用户可见字符

```sql
SELECT
    CHAR_LENGTH(_utf8mb4'数据库') AS character_count,
    OCTET_LENGTH(_utf8mb4'数据库') AS byte_count,
    BIT_LENGTH(_utf8mb4'数据库') AS bit_count;
```

结果分别是 3、9 和 72。`CHAR_LENGTH()` 统计字符, `LENGTH()` 与 `OCTET_LENGTH()` 统计字节, `BIT_LENGTH()` 统计位。

Unicode 中一个用户感知字符可能由多个码点组成, 例如带组合音标的文字或 emoji 序列。数据库的字符长度约束不等同于前端看到的字形数量, 需要按产品规则额外校验。

### 行大小限制

MySQL 表的逻辑行大小上限约为 65,535 Byte, 该限制由多列共享并包含部分内部开销。InnoDB 还受页大小和行格式限制。即使单列语法允许很大的 `VARCHAR`, 建表时也可能得到 `Row size too large`。

`TEXT` / `BLOB` 的内容不按完整理论长度计入 MySQL 的 65,535 Byte 行定义限制, 但 InnoDB 记录仍保存长度或行外指针。长值是否以及如何移到页外, 取决于行格式、页大小和值本身; 不要把它简化成“VARCHAR 总在行内, TEXT 总在行外”。

## BINARY 与 VARBINARY

`BINARY` / `VARBINARY` 保存原始字节, 不做字符集转换, 比较时每个字节都重要。

- `BINARY(M)` 会用 `0x00` 补齐到固定长度。查询结果保留这些补位字节。
- `VARBINARY(M)` 不补位, 适合长度会变化的二进制值。
- 二进制值的长度用 `OCTET_LENGTH()` 或 `LENGTH()` 检查。
- 不要用 `CHAR` 保存任意二进制。字符集转换可能拒绝或改变字节。

```sql
SELECT
    HEX(CAST(X'4142' AS BINARY(4))) AS padded_binary,
    HEX(CAST(X'4142' AS BINARY)) AS binary_value;
```

固定宽度 hash 适合 `BINARY`, 因为每行长度相同且字节比较明确。随机 token 如果长度不固定则使用 `VARBINARY`。

## TEXT 与 BLOB

`TEXT` 保存带字符集和 collation 的大文本; `BLOB` 保存无编码含义的任意字节。它们具有对应的四个容量等级。

选型时使用能覆盖真实上限的最小等级, 但不要只为节省长度前缀的 1 或 2 Byte 而压缩业务上限。更重要的是限制上传大小、避免无条件读取大列、评估备份与复制流量。

### 默认值

MySQL 8.0.13 以后, `TEXT` / `BLOB` 可以使用表达式默认值; 即使表达式结果是字面量, 也要用表达式形式。MySQL 8.4 可写为:

```sql
notes TEXT NOT NULL DEFAULT (''),
payload BLOB NOT NULL DEFAULT (X'')
```

这不意味着应该给大对象设置庞大默认内容。多数大文本或二进制载荷更适合明确 `NULL` 与空值的业务语义。

### 数据库 BLOB 与对象存储

把文件放入 BLOB 可以获得与同一事务内元数据的一致提交, 权限和备份也集中。但大对象会放大 Buffer Pool 污染、binlog、复制、备份和网络成本。

大文件通常可把对象主体放在对象存储, 数据库保存对象键、大小、媒体类型和校验摘要。若必须要求元数据与字节内容强事务一致, 或对象较小且访问模式可控, BLOB 仍是合理选择。不要把任何一方写成绝对规则。

## 字符集与排序规则

### utf8mb4 与 utf8mb3
MySQL 8.4 新项目应显式使用 `utf8mb4`。在该版本中, 历史名称 `utf8` 仍是已弃用的 `utf8mb3` 的别名; `utf8mb3` 不能保存完整 Unicode 和四字节字符。不要仅写 `utf8` 并假设它等于 `utf8mb4`。

```sql
CREATE TABLE localized_text (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    body MEDIUMTEXT NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

字符集可以在 server、database、table 和 column 层继承。连接还有 `character_set_client`、`character_set_connection` 和 `character_set_results`; 数据在写入列之前可能已经经过连接层转换。排查乱码时应同时检查:

```sql
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';
SHOW CREATE TABLE localized_text;
```

### collation 后缀

| 后缀 | 含义 | 示例用途 |
| :--- | :--- | :--- |
| `_ai_ci` | accent-insensitive, case-insensitive | 自然语言搜索、大小写不敏感名称 |
| `_as_cs` | accent-sensitive, case-sensitive | 需要区分大小写与重音的字符标识 |
| `_bin` | 按该字符集的二进制权重比较 | 机器代码或要求稳定字符区分的值 |

`utf8mb4_0900_ai_ci` 中, 某些大小写和重音差异会比较为相同。这同时影响 `WHERE`、`ORDER BY`、`GROUP BY`、`DISTINCT` 和 `UNIQUE`。登录名、邮箱、文件名和外部代码是否区分大小写必须由业务明确, 不能只沿用数据库默认值。

`VARBINARY` 的逐字节比较与字符列的 `_bin` collation 仍不是同一概念。后者仍先按字符集解释输入, 前者完全没有字符集转换。

### 修改字符集

`ALTER TABLE ... CONVERT TO CHARACTER SET ...` 可能重建表、改变索引字节数并触发数据转换。转换前应:

1. 备份并确认源字节实际使用的编码。
2. 检查无法转换的字符和转换后的最大字节长度。
3. 检查索引键长度、唯一性语义和 collation 变化。
4. 在预发布环境测量 DDL 算法、元数据锁、binlog 和复制延迟。
5. 转换后用 `SHOW CREATE TABLE`、抽样数据和校验查询复核。

## 可执行建表示例

下面同时演示机器代码、自然语言、长文本和原始 token:

```sql
DROP TEMPORARY TABLE IF EXISTS string_design_demo;

CREATE TEMPORARY TABLE string_design_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    country_code CHAR(2)
        CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    display_name VARCHAR(80)
        CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci NOT NULL,
    external_key VARCHAR(64)
        CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    summary TEXT
        CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci NULL,
    token_hash VARBINARY(32) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_string_design_external_key (external_key),
    KEY idx_string_design_display_name (display_name),
    KEY idx_string_design_summary_prefix (summary(100))
) ENGINE = InnoDB;

INSERT INTO string_design_demo
    (country_code, display_name, external_key, summary, token_hash)
VALUES
    ('CN', '数据库工程', 'USER-000042', '字段类型应表达真实语义。',
     UNHEX(SHA2('one-time-token', 256)));

SELECT
    display_name,
    CHAR_LENGTH(display_name) AS display_name_chars,
    OCTET_LENGTH(display_name) AS display_name_bytes,
    HEX(token_hash) AS token_hash_hex
FROM string_design_demo;
```

`summary(100)` 是前缀索引, 对非二进制字符串的长度按字符解释, 但实际索引字节数受字符集影响。它只能覆盖前 100 个字符, 不能保证整列唯一, 也未必有足够选择性。先用真实数据测量前缀基数。

## Hash 示例

SHA-256 输出 256 bit, 即 32 Byte。`SHA2()` 返回十六进制文本, 用 `UNHEX()` 转为紧凑字节:

```sql
DROP TEMPORARY TABLE IF EXISTS hash_demo;

CREATE TEMPORARY TABLE hash_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    payload_sha256 BINARY(32) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_hash_demo_sha256 (payload_sha256)
) ENGINE = InnoDB;

INSERT INTO hash_demo (payload_sha256)
VALUES (UNHEX(SHA2('payload-v1', 256)));

SELECT HEX(payload_sha256) AS sha256_hex
FROM hash_demo;
```

`CHAR(64)` 也能保存 SHA-256 十六进制文本, 但需要 64 Byte; `BINARY(32)` 更紧凑。加密密码不要直接使用普通 SHA-256: 应使用 Argon2id、bcrypt、scrypt 或 PBKDF2 等专用密码哈希, 并保存算法参数和 salt。

## UUID 示例

UUID 有可读文本和紧凑二进制两种常见设计:

| 设计 | 空间 | 特点 |
| :--- | :--- | :--- |
| `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin` | 36 Byte 左右 | 可直接阅读, 带连字符 |
| `BINARY(16)` | 16 Byte | 更紧凑, 需要转换函数 |

```sql
DROP TEMPORARY TABLE IF EXISTS uuid_demo;

CREATE TEMPORARY TABLE uuid_demo (
    id BINARY(16) NOT NULL,
    label VARCHAR(64) NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB;

INSERT INTO uuid_demo (id, label)
VALUES (UUID_TO_BIN(UUID(), 1), 'generated by MySQL');

SELECT BIN_TO_UUID(id, 1) AS uuid_text, label
FROM uuid_demo;
```

`UUID_TO_BIN(..., 1)` 与 `BIN_TO_UUID(..., 1)` 的 swap flag 必须一致。swap 对 MySQL `UUID()` 产生的时间型 UUID 有助于把高变化部分调整到后方, 改善索引局部性; 对随机 UUID 不会凭空产生时间局部性。

## BLOB 示例

```sql
DROP TEMPORARY TABLE IF EXISTS file_blob_demo;

CREATE TEMPORARY TABLE file_blob_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    media_type VARCHAR(100)
        CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    body MEDIUMBLOB NOT NULL,
    sha256 BINARY(32) NOT NULL,
    PRIMARY KEY (id),
    KEY idx_file_blob_sha256 (sha256)
) ENGINE = InnoDB;

INSERT INTO file_blob_demo (media_type, body, sha256)
VALUES (
    'application/octet-stream',
    X'000102FF',
    UNHEX(SHA2(X'000102FF', 256))
);

SELECT
    media_type,
    OCTET_LENGTH(body) AS body_bytes,
    HEX(body) AS body_hex,
    HEX(sha256) AS sha256_hex
FROM file_blob_demo;
```

应用上传时应流式绑定 BLOB, 设置业务大小上限, 校验实际媒体格式, 并避免列表接口无条件 `SELECT body`。

## 索引与查询

- 短 `VARCHAR` 可以建完整 B-Tree 索引; 索引列顺序应由查询条件和排序决定。
- `TEXT` / `BLOB` 建 B-Tree 索引时通常要指定前缀长度。文本前缀按字符声明, 二进制前缀按字节声明。
- InnoDB 常见最大索引键长度是 3,072 Byte, 但实际限制还受页大小、行格式和版本影响。`utf8mb4` 应按每字符最多 4 Byte 做上界检查。
- `UNIQUE (long_text(100))` 只保证前缀唯一, 不保证完整内容唯一。
- 自然语言正文检索可评估 `FULLTEXT` 索引或外部搜索系统; 普通 B-Tree 无法有效支持 `LIKE '%keyword%'`。
- 查询列表显式列出字段, 避免 `SELECT *` 把大文本或 BLOB 无条件传输到应用。
- 对长值做排序、分组、临时表和重复传输可能消耗大量内存与 I/O, 应用真实数据验证执行计划。

## 常见错误

- 把 `VARCHAR(M)` 的 `M` 当成字节数。
- 宣称 `VARCHAR` 最大值无条件是 65,535 个字符。
- 认为 `TEXT` 永远在行外、`VARCHAR` 永远在行内。
- 用 `CHAR` 保存尾随空格有业务意义的值。
- 用普通字符串保存二进制摘要或密文, 导致空间翻倍或字符集转换。
- 使用 `utf8` 名称却误以为一定是完整 `utf8mb4`。
- 忽略 collation 对大小写、重音、排序和唯一键的影响。
- 在前缀唯一索引上误以为整列都唯一。
- 把 `LONGTEXT` / `LONGBLOB` 的理论上限当成安全上传上限。
- 列表查询无条件读取正文和 BLOB。

## 选型检查表

- 数据是字符还是任意字节?
- 最大长度按字符、字节还是用户感知字形定义?
- 是否真的定长, 以及填充字节是否会改变语义?
- 字符比较是否区分大小写、重音和尾随空格?
- 唯一性应按自然语言规则还是精确机器代码规则判断?
- 列是否需要完整索引、前缀索引、全文索引或根本不应索引?
- 大对象是否应进入数据库, 对 binlog、复制和备份的成本是否可接受?
- 驱动和 API 是否会进行字符集转换、Base64 编码或十六进制转换?
