# MySQL 定点与位类型

`DECIMAL` / `NUMERIC` 用于精确十进制数, `BIT` 用于固定宽度位串, `BOOL` / `BOOLEAN` 则只是 `TINYINT(1)` 的语法别名。它们看起来都能保存 `0` 和 `1`, 但存储语义、计算方式和客户端映射完全不同。

## 类型速览

| 类型 | 定义范围 | 存储语义 | 典型用途 |
| :--- | :--- | :--- | :--- |
| `DECIMAL(M,D)` | `1 <= M <= 65`, `0 <= D <= 30`, `D <= M` | 精确十进制, `M` 是总位数, `D` 是小数位数 | 金额、税率、精确测量值 |
| `NUMERIC(M,D)` | 与 `DECIMAL(M,D)` 相同 | `DECIMAL` 的同义词 | 需要贴近标准 SQL 命名时 |
| `BIT(M)` | `1 <= M <= 64`, 省略 `M` 时为 `BIT(1)` | 固定宽度位串, 大约占 `CEIL(M / 8)` Byte | 协议位、紧凑的静态权限位掩码 |
| `BOOL` / `BOOLEAN` | 与 `TINYINT(1)` 相同 | 1 Byte 整数, `1` 只是历史显示宽度, 不是值域约束 | 业务真假标记 |

## DECIMAL 与 NUMERIC

### 精度、标度与范围

`DECIMAL(M,D)` 中:

- `M` 是十进制总位数, 包含整数部分和小数部分。
- `D` 是小数位数, 因此整数部分最多有 `M - D` 位。
- 省略参数时, `DECIMAL` 等价于 `DECIMAL(10,0)`。
- `NUMERIC` 在 MySQL 中与 `DECIMAL` 同义。

有符号 `DECIMAL(M,D)` 的最大绝对值是:

```text
10^(M-D) - 10^(-D)
```

例如 `DECIMAL(10,2)` 有 8 位整数和 2 位小数, 可表示 `-99999999.99` 到 `99999999.99`。`DECIMAL(6,6)` 没有非零整数位, 可表示 `-0.999999` 到 `0.999999`。

新设计不要依赖 `DECIMAL UNSIGNED`。这个属性在 MySQL 8.x 已被弃用; 非负规则应写成可读、可验证的 `CHECK (amount >= 0)`。

### 压缩存储

MySQL 以二进制格式压缩保存 `DECIMAL`, 不是逐字符保存。整数部分和小数部分分别按每 9 位一组计算空间:

| 剩余十进制位数 | 需要的字节数 |
| :--- | :--- |
| 0 | 0 |
| 1 到 2 | 1 |
| 3 到 4 | 2 |
| 5 到 6 | 3 |
| 7 到 9 | 4 |

每个完整的 9 位组占 4 Byte。例如 `DECIMAL(19,4)` 的整数部分有 15 位, 需要 `4 + 3` Byte; 小数部分 4 位需要 2 Byte, 合计 9 Byte。符号编码在该二进制表示中, 不要再额外加一个字符字节。

空间只是选型因素之一。字段还必须覆盖累计值、税额、汇率和中间计算结果, 否则最终值没溢出, 中间表达式也可能先溢出。

### 舍入、溢出与严格模式

`DECIMAL` 避免的是二进制浮点误差, 并不代表数据库会替业务决定舍入规则。

- 写入的小数位多于 `D` 时, MySQL 会把值转换到列的标度; 精确值通常按精确数学规则舍入。
- 整数位超出范围时, 严格 SQL 模式会报错; 非严格模式可能截到边界并给出警告。
- `ROUND()`、乘法和除法会产生新的结果精度与标度。结算点应显式 `ROUND` 或 `CAST`, 并由业务定义舍入模式和发生时机。
- 十进制字面量如 `19.95` 属于精确值; 科学计数法字面量通常走近似值路径。应用层也不要先用 `double` 计算后再写入 `DECIMAL`。

生产环境应启用严格模式, 并把边界值、负值、过多小数位和溢出作为测试用例。

### 可执行金额示例

下面的临时表演示单价、可分割数量、税率和最终结算值。临时表只在当前连接中存在。

```sql
DROP TEMPORARY TABLE IF EXISTS product_price_demo;

CREATE TEMPORARY TABLE product_price_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    currency CHAR(3) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    unit_price DECIMAL(19,4) NOT NULL,
    quantity DECIMAL(12,3) NOT NULL,
    tax_rate DECIMAL(9,6) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_product_price_nonnegative CHECK (unit_price >= 0),
    CONSTRAINT chk_product_quantity_positive CHECK (quantity > 0),
    CONSTRAINT chk_product_tax_rate CHECK (tax_rate BETWEEN 0 AND 1)
) ENGINE = InnoDB;

INSERT INTO product_price_demo (currency, unit_price, quantity, tax_rate)
VALUES ('CNY', 19.9900, 3.000, 0.130000);

SELECT
    unit_price * quantity AS net_amount,
    unit_price * quantity * tax_rate AS tax_amount,
    CAST(ROUND(unit_price * quantity * (1 + tax_rate), 2) AS DECIMAL(19,2))
        AS settlement_amount
FROM product_price_demo;
```

这组数据的 `net_amount` 是 `59.9700000`, 税后结算值是 `67.77`。`currency` 不能省略: 不同币种的小数位和舍入规则可能不同。

### DECIMAL 与最小货币单位整数

金额并非只能使用一种方案:

| 方案 | 优点 | 风险与边界 |
| :--- | :--- | :--- |
| `DECIMAL(19,4)` | 直接表达十进制金额和小数费率, SQL 可读性高 | 必须统一标度和舍入点; Java 应使用 `BigDecimal` |
| `BIGINT` 保存最小货币单位 | 整数运算简单、精确, 对固定标度币种很方便 | 必须同时保存币种和标度; 某些币种不是 2 位小数; 乘除、中间值和溢出仍要设计 |

因此不应写成“金额绝不能用整数”或“金额一律用 `DECIMAL(10,2)`”。应从币种、最大金额、最小计价单位、运算链和客户端类型共同推导。

### 客户端边界

- Java/JDBC 使用 `BigDecimal`、`setBigDecimal()` 和 `getBigDecimal()`, 不要经过 `double`。
- JavaScript `Number` 无法精确承载很大的 65 位十进制数。API 可传十进制字符串, 再由 decimal 库处理。
- 某些驱动默认把 `DECIMAL` 返回为字符串以保护精度; 不要把它误判为数据库类型错误。
- 比较前统一标度和业务舍入规则。Java 的 `BigDecimal.equals()` 还会比较标度, `compareTo()` 的语义不同。

## DECIMAL 与 FLOAT / DOUBLE 对照

| 维度 | `DECIMAL` / `NUMERIC` | `FLOAT` / `DOUBLE` |
| :--- | :--- | :--- |
| 数学模型 | 十进制精确值 | 二进制近似值 |
| 适合 | 金额、账务、精确比例、需要可重复十进制结果的值 | 传感器、科学计算、统计近似值 |
| 等值比较 | 在相同转换规则下可做精确比较 | 通常应使用容差或误差区间 |
| 空间 | 由 `M,D` 按十进制位组决定 | `FLOAT` 4 Byte, `DOUBLE` 8 Byte |
| 主要风险 | 精度/标度不足、业务舍入点错误 | 表示误差、累计误差、直接 `=` 比较 |

可执行对照:

```sql
DROP TEMPORARY TABLE IF EXISTS numeric_compare_demo;

CREATE TEMPORARY TABLE numeric_compare_demo (
    exact_value DECIMAL(10,2) NOT NULL,
    approximate_value DOUBLE NOT NULL
);

INSERT INTO numeric_compare_demo VALUES
    (0.10, 0.10),
    (0.20, 0.20),
    (0.30, 0.30);

SELECT
    SUM(exact_value) AS exact_sum,
    SUM(approximate_value) AS approximate_sum,
    ABS(SUM(approximate_value) - 0.60) < 1e-12 AS within_tolerance
FROM numeric_compare_demo;
```

不要依赖客户端显示的小数位判断 `DOUBLE` 是否精确; 显示层可能已经格式化或舍入。

## BIT

### 位宽、存储与字面量

`BIT(M)` 保存固定宽度位串, `M` 为 1 到 64。常用字面量有 `b'0101'`、`0b0101` 和十六进制字面量。`BIT(8)` 约占 1 Byte, `BIT(9)` 约占 2 Byte。

驱动常把 `BIT` 返回为字节数组、二进制字符串或布尔值, 具体行为与驱动及位宽有关。排查时显式转换:

```sql
SELECT
    CAST(b'00000101' AS UNSIGNED) AS decimal_value,
    LPAD(BIN(CAST(b'00000101' AS UNSIGNED)), 8, '0') AS bit_text,
    HEX(b'00000101') AS hex_value;
```

### 可执行权限位掩码示例

约定位 0 到位 3 分别表示 `read=1`、`write=2`、`delete=4`、`admin=8`:

```sql
DROP TEMPORARY TABLE IF EXISTS permission_demo;

CREATE TEMPORARY TABLE permission_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    subject_name VARCHAR(64) NOT NULL,
    permission_mask BIT(8) NOT NULL DEFAULT b'00000000',
    PRIMARY KEY (id)
) ENGINE = InnoDB;

INSERT INTO permission_demo (subject_name, permission_mask)
VALUES ('report-worker', b'00000101');

SELECT
    subject_name,
    CAST(permission_mask AS UNSIGNED) AS mask_value,
    LPAD(BIN(CAST(permission_mask AS UNSIGNED)), 8, '0') AS mask_bits,
    (CAST(permission_mask AS UNSIGNED) & 1) <> 0 AS can_read,
    (CAST(permission_mask AS UNSIGNED) & 2) <> 0 AS can_write,
    (CAST(permission_mask AS UNSIGNED) & 4) <> 0 AS can_delete
FROM permission_demo;

UPDATE permission_demo
SET permission_mask = CAST(permission_mask AS UNSIGNED) | 2
WHERE subject_name = 'report-worker';

UPDATE permission_demo
SET permission_mask = CAST(permission_mask AS UNSIGNED) & 251
WHERE subject_name = 'report-worker';
```

`251` 是 8 位全 1 掩码 `255` 清除值为 `4` 的 delete 位后的结果。位定义必须集中管理并配套测试。成员经常变化、需要成员属性、需要按单个权限高频查询或需要外键完整性时, 应改用权限表和关联表。

## BOOL 与 BOOLEAN

MySQL 8.4 中 `BOOL`、`BOOLEAN` 都是 `TINYINT(1)` 的别名。它们不是独立的强布尔类型:

- `TRUE` 和 `FALSE` 分别是常量 `1` 和 `0`。
- 没有约束时, `BOOLEAN` 列仍可保存 `2`、`-1` 等 `TINYINT` 值。
- SQL 条件把 `0` 视为假、非零视为真、`NULL` 视为未知。
- `2 = TRUE` 比较的是 `2 = 1`, 结果为假; `2 IS TRUE` 判断真值, 结果为真。

需要严格的二值字段时同时使用 `NOT NULL`、显式默认值和 `CHECK`:

```sql
DROP TEMPORARY TABLE IF EXISTS boolean_demo;

CREATE TEMPORARY TABLE boolean_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (id),
    CONSTRAINT chk_boolean_demo_active CHECK (is_active IN (0, 1))
) ENGINE = InnoDB;

INSERT INTO boolean_demo (is_active) VALUES (TRUE), (FALSE);

SELECT
    2 = TRUE AS equality_result,
    2 IS TRUE AS truth_test_result;
```

`BIT(1)` 更接近一个位, `BOOLEAN` 更接近一个业务真假值。由于 JDBC 和其他驱动对 `BIT(1)` 的映射可能不同, 普通业务开关通常使用带 `CHECK` 的 `BOOLEAN` / `TINYINT`, 协议位或静态位掩码才使用 `BIT`。

## 选型检查表

- 值是否必须十进制精确? 若是, 先考虑 `DECIMAL` 或有清晰标度的整数。
- `M,D` 是否覆盖未来最大值和所有中间结果?
- 舍入是在单项、税额、汇总还是最终结算发生?
- 应用、消息和 JSON API 是否会把精确数偷偷转成二进制浮点?
- 位掩码是否真的稳定、紧凑且不需要关系查询?
- 布尔字段是否通过 `NOT NULL`、`DEFAULT` 和 `CHECK` 限制为 0/1?
