# MySQL 空间数据类型

本文以 MySQL 8.4 LTS 和 InnoDB 为基线. 空间数据类型用于保存带空间参考系的点, 线, 面以及它们的集合. 它们不是经纬度字符串的别名, 而是可由 MySQL 校验格式, 计算空间关系并建立 R-tree 空间索引的原生类型.

## 类型作用

MySQL 的空间类型形成一个层次. `GEOMETRY` 是通用父类型, 其余类型限制列中只能保存特定几何形状.

| 类型 | 维度 | 表达对象 | 典型用途 |
| :--- | :---: | :--- | :--- |
| `GEOMETRY` | 混合 | 任意受支持的几何值 | 类型确实可能变化的通用空间载荷 |
| `POINT` | 0 | 单个坐标点 | 门店, 设备, 车辆当前位置 |
| `LINESTRING` | 1 | 按顺序连接的一条折线 | 道路中心线, 轨迹, 管线 |
| `POLYGON` | 2 | 一个外环和可选内环构成的面 | 行政区, 配送范围, 地块 |
| `MULTIPOINT` | 0 | 多个互相独立的点 | 采样点集合, 站点组 |
| `MULTILINESTRING` | 1 | 多条独立折线 | 分段道路网, 多段河流 |
| `MULTIPOLYGON` | 2 | 多个独立多边形 | 飞地行政区, 多块服务区域 |
| `GEOMETRYCOLLECTION` | 混合 | 不同几何类型的集合 | 同一对象同时携带点, 线, 面 |

应优先选择最具体的类型. 门店位置应使用 `POINT`, 不要因为 `GEOMETRY` 能容纳点就放弃列级类型约束. 只有同一列确实需要存放不同形状时才使用 `GEOMETRY` 或 `GEOMETRYCOLLECTION`.

## 存储, 格式与约束

### 内部值不是 WKT 文本

MySQL 在空间列中保存二进制几何值和 SRID 元数据. WKT, WKB, GeoJSON 是输入输出格式, 不是空间列本身的存储类型.

常用转换函数:

- `ST_GeomFromText(wkt, srid, options)`: 从 WKT 构造几何值.
- `ST_AsText(geometry, options)`: 输出便于阅读的 WKT.
- `ST_GeomFromGeoJSON()` 和 `ST_AsGeoJSON()`: 与 GeoJSON 转换.
- `ST_SRID()`: 读取几何值的 SRID.
- `ST_GeometryType()`: 读取具体几何类型.

不要把 `'121.4737,31.2304'` 或 GeoJSON 字符串直接保存到 `VARCHAR` 后再期待空间索引工作.

### SRID 0 与 SRID 4326

SRID 表示 Spatial Reference System Identifier.

- SRID 0 是 MySQL 的未定义笛卡尔平面. 单位没有地理含义.
- SRID 4326 是 WGS 84 地理坐标系, 常用于全球经纬度.
- 列定义中的 `SRID 4326` 会拒绝 SRID 不匹配的值.
- 两个几何值参与空间运算时通常必须使用同一 SRID, 否则会报错.

EPSG:4326 的 SRS 定义带有轴顺序. 许多应用和 GeoJSON 使用 `longitude, latitude`, 而不能靠读者猜测坐标次序. 本文所有 WKT 构造和输出都显式写:

```sql
'axis-order=long-lat'
```

例如上海人民广场附近的点写成:

```sql
ST_GeomFromText(
    'POINT(121.4737 31.2304)',
    4326,
    'axis-order=long-lat'
)
```

第一个数是 longitude, 第二个数是 latitude. 对地理 SRS, MySQL 还会检查经纬度是否落在 SRS 允许范围内.

### 几何有效性与拓扑有效性

空间值能被 WKT 解析, 不代表几何一定在业务上有效.

- `LINESTRING` 至少需要足够的不同点形成线.
- `POLYGON` 的环必须闭合, 即首尾点相同.
- 自相交多边形可能通过格式解析, 但拓扑无效.
- 洞环与外环的方向, 相交关系和包含关系需要验证.
- 对无效几何执行某些精确关系函数, 结果可能无意义或报错.

可以在写入前执行 `ST_IsValid()`, 并对重要面数据增加 CHECK. 还应在应用或导入流程中给出可定位的错误信息.

## 八种类型的可执行 DDL

下面的表逐列限定八种空间类型. 它用于学习和导入验证, 业务表通常不应把所有类型堆在同一行.

```sql
CREATE TABLE spatial_type_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    any_geometry GEOMETRY SRID 4326,
    one_point POINT SRID 4326,
    one_route LINESTRING SRID 4326,
    one_area POLYGON SRID 4326,
    point_group MULTIPOINT SRID 4326,
    route_group MULTILINESTRING SRID 4326,
    area_group MULTIPOLYGON SRID 4326,
    mixed_group GEOMETRYCOLLECTION SRID 4326,

    PRIMARY KEY (id)
) ENGINE = InnoDB;
```

## 八种类型的可执行 INSERT

下面所有坐标都采用 SRID 4326, 并显式按 longitude, latitude 解释.

```sql
INSERT INTO spatial_type_demo (
    any_geometry,
    one_point,
    one_route,
    one_area,
    point_group,
    route_group,
    area_group,
    mixed_group
)
VALUES (
    ST_GeomFromText(
        'POINT(121.4737 31.2304)',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'POINT(121.4737 31.2304)',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'LINESTRING(121.4600 31.2200, 121.4737 31.2304, 121.4900 31.2400)',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'POLYGON((121.4600 31.2200, 121.4900 31.2200, 121.4900 31.2450, 121.4600 31.2450, 121.4600 31.2200))',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'MULTIPOINT(121.4700 31.2250, 121.4800 31.2350, 121.4850 31.2280)',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'MULTILINESTRING((121.4600 31.2200, 121.4700 31.2300), (121.4800 31.2350, 121.4900 31.2450))',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'MULTIPOLYGON(((121.4500 31.2100, 121.4600 31.2100, 121.4600 31.2200, 121.4500 31.2200, 121.4500 31.2100)), ((121.4800 31.2350, 121.4900 31.2350, 121.4900 31.2450, 121.4800 31.2450, 121.4800 31.2350)))',
        4326,
        'axis-order=long-lat'
    ),

    ST_GeomFromText(
        'GEOMETRYCOLLECTION(POINT(121.4737 31.2304), LINESTRING(121.4600 31.2200, 121.4900 31.2400))',
        4326,
        'axis-order=long-lat'
    )
);
```

每个值的作用:

1. `any_geometry` 当前保存 POINT, 但同列下一行也可保存其他几何子类型.
2. `one_point` 只能保存 POINT, 可作为门店或设备位置.
3. `one_route` 保存一条有顺序的路线, 点的顺序决定线路方向.
4. `one_area` 保存单个面, WKT 环的首尾坐标相同.
5. `point_group` 保存多个独立点, 点之间没有线路连接语义.
6. `route_group` 保存多条相互独立的折线.
7. `area_group` 保存多个相互独立的面.
8. `mixed_group` 同时保存一个点和一条线, 适合真正的异构集合.

## 可执行 SELECT

```sql
SELECT
    id,
    ST_GeometryType(any_geometry) AS actual_type,
    ST_SRID(one_point) AS point_srid,
    ST_AsText(one_point, 'axis-order=long-lat') AS point_wkt,
    ST_AsGeoJSON(one_route) AS route_geojson,
    ST_Area(one_area) AS area_default_unit
FROM spatial_type_demo;
```

读取时仍应保留 SRID 信息. WKT 本身通常不携带 SRID, 单独传输 WKT 时要同时传递 SRID, 或使用约定明确的 GeoJSON/API schema.

## 生产化表设计

下面用门店位置和服务区域展示具体类型, 约束与索引:

```sql
CREATE TABLE store_service_area (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    store_code VARCHAR(32) NOT NULL,
    store_name VARCHAR(128) NOT NULL,

    location POINT NOT NULL SRID 4326,
    service_area POLYGON NOT NULL SRID 4326,

    created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    PRIMARY KEY (id),
    UNIQUE KEY uk_store_service_area_code (store_code),

    SPATIAL INDEX sp_store_location (location),
    SPATIAL INDEX sp_store_service_area (service_area),

    CONSTRAINT chk_store_service_area_valid
        CHECK (ST_IsValid(service_area))
) ENGINE = InnoDB
  DEFAULT CHARACTER SET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

空间索引列声明为 `NOT NULL`, 同时通过 `SRID 4326` 限定参考系. 对 InnoDB, 这样的受限列能给优化器和空间函数更明确的语义.

写入一间门店:

```sql
INSERT INTO store_service_area (
    store_code,
    store_name,
    location,
    service_area
)
VALUES (
    'SHA-001',
    'People Square Store',
    ST_GeomFromText(
        'POINT(121.4737 31.2304)',
        4326,
        'axis-order=long-lat'
    ),
    ST_GeomFromText(
        'POLYGON((121.4500 31.2100, 121.5000 31.2100, 121.5000 31.2550, 121.4500 31.2550, 121.4500 31.2100))',
        4326,
        'axis-order=long-lat'
    )
);
```

## SPATIAL INDEX 的作用与限制

InnoDB 的 `SPATIAL INDEX` 使用几何对象的 Minimum Bounding Rectangle, 简称 MBR, 组织 R-tree. 它适合先快速筛出包围盒可能相交的候选行.

它与普通 B-tree 索引不同:

- 不按字符串或数值大小排序.
- 不能把空间列与普通列拼成一个常规联合空间索引.
- 对复杂线和多边形, MBR 命中不等于真实几何相交.
- `ORDER BY ST_Distance(...)` 不会自动变成传统意义上的距离索引扫描.
- 高度重叠, 覆盖范围很大的几何对象会降低选择性.

实践中通常分两步:

1. 用可利用空间索引的 MBR 谓词做粗筛.
2. 用精确空间关系或距离函数过滤候选集.

### 范围粗筛加精确距离

```sql
SET @center = ST_GeomFromText(
    'POINT(121.4737 31.2304)',
    4326,
    'axis-order=long-lat'
);

SET @search_box = ST_GeomFromText(
    'POLYGON((121.4400 31.2000, 121.5100 31.2000, 121.5100 31.2600, 121.4400 31.2600, 121.4400 31.2000))',
    4326,
    'axis-order=long-lat'
);

SELECT
    id,
    store_code,
    store_name,
    ST_Distance(location, @center, 'metre') AS distance_metres
FROM store_service_area
WHERE MBRContains(@search_box, location)
  AND ST_Distance(location, @center, 'metre') <= 3000
ORDER BY distance_metres;
```

经纬度一度对应的实际距离随纬度变化, 所以不要在业务代码中把 `longitude BETWEEN ...` 和 `latitude BETWEEN ...` 的差值直接当米. 上例的 MBR 只用于候选筛选, 最终半径由地理距离函数判定.

### 服务区域包含判断

```sql
SET @customer_location = ST_GeomFromText(
    'POINT(121.4800 31.2350)',
    4326,
    'axis-order=long-lat'
);

SELECT
    id,
    store_code,
    store_name
FROM store_service_area
WHERE MBRContains(service_area, @customer_location)
  AND ST_Contains(service_area, @customer_location);
```

第一条条件使用包围盒粗筛, 第二条条件执行真实几何包含判断. 对凹多边形或带洞多边形, 只写 `MBRContains` 可能产生假阳性.

查询后用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 检查是否使用 `sp_store_location` 或 `sp_store_service_area`. 函数参数方向也会影响优化器能否把谓词匹配到索引列.

## 各类型的查询函数选择

| 目标 | 推荐函数 | 说明 |
| :--- | :--- | :--- |
| 判断两个点是否相同 | `ST_Equals()` | 不要比较 WKT 字符串 |
| 点是否在面内 | `ST_Contains()` 或 `ST_Within()` | 注意边界点语义 |
| 几何是否相交 | `ST_Intersects()` | 精确关系, 可先用 MBR 粗筛 |
| 线长度 | `ST_Length()` | 地理 SRS 下按支持的单位输出 |
| 面积 | `ST_Area()` | 只对面类型有意义 |
| 点间或对象间距离 | `ST_Distance()` | 两个值必须使用兼容 SRID |
| 取 POINT 横纵坐标 | `ST_Longitude()`, `ST_Latitude()` | 适用于地理 SRS 的 POINT |
| 检查拓扑有效性 | `ST_IsValid()` | 导入和约束阶段使用 |
| 粗略包围盒判断 | `MBRContains()`, `MBRIntersects()` | 适合空间索引候选筛选 |

边界点是否算作包含, 相交还是接触, 要依据 OGC 空间关系定义选择 `ST_Contains`, `ST_Covers`, `ST_Touches` 等函数, 不要只凭函数名猜测.

## 适用与不适用场景

### 适用

- 门店, 车辆, 设备和事件发生点.
- 道路, 轨迹, 管线和航线.
- 行政区, 配送区, 围栏和地块.
- 需要包含, 相交, 邻近或距离过滤的业务.
- 数据需要明确 SRID 并由数据库执行基础空间计算.

### 不适用或需要谨慎

- 只是展示且永不做空间计算的普通地址文本. 地址和坐标应分列保存.
- 只有国家码, 城市码等离散区域标识的业务. 普通外键更合适.
- 需要复杂地图渲染瓦片, 网络路径规划, 高级投影分析或专业 GIS 工作流. 应评估专用 GIS 服务.
- 持续高频写入巨大轨迹到单个 LINESTRING. 通常应按时间分行保存轨迹点或分段.
- 把不同 SRID 的来源数据未经转换直接混入同一列.

## 常见错误

1. 用两个 `VARCHAR` 或一个逗号字符串保存经纬度, 无法可靠校验和使用空间索引.
2. 把 latitude, longitude 和 longitude, latitude 混用, 又没有显式 axis-order.
3. 构造值时省略 SRID, 导致 SRID 0 数据无法写入 `SRID 4326` 列.
4. 对不同 SRID 的几何值直接执行距离或相交计算.
5. 对门店位置使用宽泛的 `GEOMETRY`, 失去 `POINT` 类型约束.
6. 以为合法 WKT 就一定是拓扑有效多边形, 忽略闭环, 自相交和洞关系.
7. 只用 `MBRContains` 判定复杂多边形内点, 产生包围盒假阳性.
8. 只写精确距离条件而没有候选范围, 导致大量行执行昂贵计算.
9. 用坐标度数差直接换算固定米数, 忽略纬度和地球曲面.
10. 用 WKT 字符串相等判断几何相等. 坐标顺序或环起点不同可能表达同一几何.
11. 给可空空间列建立索引或忘记声明具体 SRID, 降低约束和索引可用性.
12. 单行保存不断增长的完整历史轨迹, 导致锁, 日志, 复制和备份成本过高.

## 设计检查清单

- 业务对象应使用 POINT, LINESTRING 还是 POLYGON, 是否误用 GEOMETRY.
- 数据来源使用什么 SRS, 是否统一转换为 SRID 4326.
- API 的坐标轴顺序是否明确定义为 longitude, latitude.
- 列是否写了 `SRID 4326` 和必要的 `NOT NULL`.
- 多边形是否闭环, 是否通过 `ST_IsValid()`.
- 查询是否先用 MBR 谓词缩小候选集, 再做精确关系或距离判断.
- 是否通过 `EXPLAIN ANALYZE` 验证空间索引被使用.
- 大型轨迹和几何对象是否分段, 是否设置大小与保留边界.
- 输出 WKT 或 GeoJSON 时是否同时保留 SRID 和 axis-order 约定.
