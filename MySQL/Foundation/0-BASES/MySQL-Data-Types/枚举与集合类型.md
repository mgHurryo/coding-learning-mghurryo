# MySQL 枚举与集合类型

`ENUM` 表示“从固定列表中选一个值”, `SET` 表示“从固定列表中选零到多个值”。两者都把候选列表写入表结构, 因而适合小而稳定的领域, 不适合频繁变化、需要成员属性或需要跨表引用的业务分类。

## 类型速览

| 类型 | 成员上限 | 内部表示 | 适合 | 不适合 |
| :--- | :--- | :--- | :--- | :--- |
| `ENUM` | 65,535 个成员 | 每个标签对应从 1 开始的序号 | 小而稳定的单选状态 | 动态字典、多语言标签、复杂状态机 |
| `SET` | 64 个成员 | 第 n 个成员对应第 n-1 位的位值 | 小而稳定的多选标志 | 标签系统、角色权限、一般多对多关系 |

## ENUM

### 定义与存储

```sql
status ENUM('pending', 'processing', 'done', 'cancelled')
    CHARACTER SET ascii COLLATE ascii_bin
    NOT NULL DEFAULT 'pending'
```

成员按声明顺序获得内部序号:

| 标签 | 内部序号 |
| :--- | :--- |
| `pending` | 1 |
| `processing` | 2 |
| `done` | 3 |
| `cancelled` | 4 |

1 到 255 个成员通常占 1 Byte, 256 到 65,535 个成员通常占 2 Byte。这个紧凑表示不等于应用应该依赖序号; 序号是表定义细节, 不是稳定的业务协议。

### 可执行示例

```sql
DROP TEMPORARY TABLE IF EXISTS ticket_enum_demo;

CREATE TEMPORARY TABLE ticket_enum_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    subject VARCHAR(200) NOT NULL,
    status ENUM('pending', 'processing', 'done', 'cancelled')
        CHARACTER SET ascii COLLATE ascii_bin
        NOT NULL DEFAULT 'pending',
    PRIMARY KEY (id),
    KEY idx_ticket_status (status)
) ENGINE = InnoDB;

INSERT INTO ticket_enum_demo (subject, status) VALUES
    ('first ticket', 'done'),
    ('second ticket', 'pending'),
    ('third ticket', 'processing');

SELECT id, subject, status, status + 0 AS internal_ordinal
FROM ticket_enum_demo
ORDER BY status;

SELECT id, subject, status
FROM ticket_enum_demo
ORDER BY CAST(status AS CHAR);
```

第一个查询按声明序号排序, 即 `pending`、`processing`、`done`、`cancelled`; 第二个查询才按标签文本排序。若业务顺序很重要, 应把顺序写入字典表, 或在查询中使用明确的 `FIELD(status, ...)` / `CASE`。

### NULL、默认值与无效值

- 允许 `NULL` 的 `ENUM` 列可保存 SQL `NULL`; 它与任何枚举标签都不同。
- `NOT NULL` 且没有显式默认值时, MySQL 可能采用第一个成员作为隐式默认值。工程上应始终显式写 `DEFAULT`, 避免成员顺序意外改变默认行为。
- 严格 SQL 模式下, 写入不在成员列表中的标签会报错。
- 非严格模式下, 无效标签可能被转换为特殊的空字符串错误值, 其内部序号为 0, 同时产生警告。
- 如果列表本身包含空字符串, 它会与序号 0 的错误值在显示上难以区分。不要把空字符串定义为正常成员。

可用下面的查询排查非严格模式遗留的序号 0:

```sql
SELECT id, status, status + 0 AS internal_ordinal
FROM ticket_enum_demo
WHERE status + 0 = 0;
```

### 字符集、排序规则与数字歧义

`ENUM` 是字符类型, 等值比较和唯一性受列的字符集与排序规则影响。`ascii_bin` 适合只允许 ASCII 且大小写敏感的机器状态码; 面向自然语言的标签不应直接充当稳定状态码。

不要使用 `'1'`、`'2'` 这类纯数字标签, 也不要用未加引号的数字给 `ENUM` 赋值。数字可能被解释为内部序号, 从而把“标签 2”和“第 2 个成员”混在一起。

创建或修改列时还应注意:

- 成员标签的尾随空格会被规范化, 不要让空格承担业务含义。
- 在大小写或重音不敏感的 collation 下, 看起来不同的标签可能比较为相同。
- 导入前确认连接字符集, 避免标签在进入列前已经被错误转换。

### 什么时候适合 ENUM

适合:

- 候选值很少且多年稳定。
- 每行只能选一个值。
- 标签没有额外属性, 或额外属性不需要由数据库维护。
- 系统明确接受 MySQL 专有类型带来的可移植性成本。

不适合:

- 运营人员需要随时新增、停用或改名。
- 每个状态还有展示名、颜色、排序、权限、语言翻译或有效期。
- 多个表要共享同一套可配置字典。
- 状态迁移需要完整状态机规则, 而不只是限制取值。

## SET

### 位图表示

```sql
capabilities SET('read', 'write', 'delete', 'export')
    CHARACTER SET ascii COLLATE ascii_bin
    NOT NULL DEFAULT ''
```

第 n 个成员对应第 n-1 位:

| 标签 | 位值 | 二进制位置 |
| :--- | :--- | :--- |
| `read` | 1 | bit 0 |
| `write` | 2 | bit 1 |
| `delete` | 4 | bit 2 |
| `export` | 8 | bit 3 |

`'read,export'` 的内部数值是 `1 + 8 = 9`。存储空间由成员数量决定:

| 成员数量 | 存储空间 |
| :--- | :--- |
| 1 到 8 | 1 Byte |
| 9 到 16 | 2 Byte |
| 17 到 24 | 3 Byte |
| 25 到 32 | 4 Byte |
| 33 到 64 | 8 Byte |

### 可执行示例

```sql
DROP TEMPORARY TABLE IF EXISTS integration_set_demo;

CREATE TEMPORARY TABLE integration_set_demo (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    integration_name VARCHAR(64) NOT NULL,
    capabilities SET('read', 'write', 'delete', 'export')
        CHARACTER SET ascii COLLATE ascii_bin
        NOT NULL DEFAULT '',
    PRIMARY KEY (id)
) ENGINE = InnoDB;

INSERT INTO integration_set_demo (integration_name, capabilities) VALUES
    ('warehouse-sync', 'export,read'),
    ('admin-console', 'read,write,delete');

SELECT
    integration_name,
    capabilities,
    capabilities + 0 AS numeric_mask,
    FIND_IN_SET('export', capabilities) > 0 AS can_export
FROM integration_set_demo;

UPDATE integration_set_demo
SET capabilities = (capabilities + 0) | 2
WHERE integration_name = 'warehouse-sync';

UPDATE integration_set_demo
SET capabilities = (capabilities + 0) & 13
WHERE integration_name = 'admin-console';
```

MySQL 输出 `SET` 时按声明顺序排列并去重, 所以输入 `'export,read'` 后通常显示为 `'read,export'`。最后一个更新中的 `13` 是四位全 1 掩码 `15` 清除值为 `2` 的 write 位后的结果。

直接写数字掩码虽然可执行, 但会把 SQL 与成员顺序强耦合。除底层协议和受控静态标志外, 应用写入通常使用标签, 并对位映射做集中定义和测试。

### NULL、空集合与无效成员

- SQL `NULL` 表示未知, 空字符串 `''` 表示已知的空集合, 两者不同。
- 严格模式下, 包含未知成员的值会报错。
- 非严格模式下, 未知成员可能被丢弃并产生警告, 从而形成“写入成功但少了标签”的隐蔽错误。
- `SET` 使用逗号分隔成员, 因此成员标签本身不应包含逗号。
- 未显式声明默认值时可能受到可空性和成员定义影响。工程上应明确写 `NULL` 或 `NOT NULL DEFAULT ''`。

`FIND_IN_SET()` 可以判断成员, 但 `SET` 仍不是规范化的关系。普通 B-Tree 索引不能像关联表索引那样高效支持任意成员组合、成员统计和成员属性查询。

### 什么时候适合 SET

适合:

- 成员最多几十个且基本不变。
- 组合只是紧凑标志, 不需要成员元数据。
- 查询以整个位图或少数固定标志为主。
- 团队能接受 MySQL 专有语义和位序耦合。

不适合:

- 标签由用户创建或经常变化。
- 需要对单个成员做外键、审计、授权、统计或有效期管理。
- 一行可能关联大量成员。
- 需要跨数据库移植或由 ORM 自然映射成集合关系。

## DDL 演进风险

`ENUM` 和 `SET` 的候选列表属于列定义。每次修改都要执行 `ALTER TABLE ... MODIFY COLUMN`, 并完整重写类型、字符集、collation、可空性、默认值和注释。漏写任何属性都可能顺带改变列行为。

### 安全演进顺序

1. 用 `SHOW CREATE TABLE` 保存当前完整定义, 并统计每个标签和异常序号。
2. 新标签优先追加到列表末尾, 不要在中间插入或重排。追加仍需在目标版本和真实表规模上验证 DDL 算法、元数据锁和复制影响。
3. 先部署同时兼容新旧标签的读路径, 再修改 DDL, 再部署写入新标签的代码。
4. 改名时先加入新标签, 分批迁移旧数据, 停止写旧标签, 最后才移除旧标签。
5. 删除或重排前确认没有旧数据、旧程序、报表、缓存、消息和副本仍依赖它。

`ENUM` 从 255 增长到 256 个成员会改变序号存储宽度。`SET` 重排成员会改变数字掩码。任何把 `status + 0` 或 `capabilities + 0` 持久化到外部系统的做法都会放大迁移风险。

示例 DDL 必须保留完整列属性:

```sql
ALTER TABLE support_ticket
    MODIFY COLUMN status
        ENUM('pending', 'processing', 'done', 'cancelled', 'archived')
        CHARACTER SET ascii COLLATE ascii_bin
        NOT NULL DEFAULT 'pending',
    ALGORITHM = INPLACE,
    LOCK = NONE;
```

某项变更是否支持 `INSTANT` / `INPLACE` 与具体版本、存储引擎、成员位置和存储宽度有关。不要把上面的算法当作所有表都能执行的保证; 在预发布环境验证, 不支持时让语句失败并重新制定发布方案。

## 替代方案

### VARCHAR 加 CHECK

MySQL 8.4 会执行 `CHECK` 约束。小而稳定、但不希望依赖内部序号的单选值可以这样设计:

```sql
CREATE TABLE workflow_item (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    status VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_workflow_item_status
        CHECK (status IN ('pending', 'processing', 'done', 'cancelled'))
) ENGINE = InnoDB;
```

它仍需 DDL 才能修改候选集合, 但存储值就是稳定标签, 排序不会暗中依赖枚举序号。

### 字典表加外键

状态需要排序、展示名、启停、描述或多语言时, 使用字典表:

```sql
CREATE TABLE workflow_status (
    code VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    sort_order SMALLINT UNSIGNED NOT NULL,
    is_enabled BOOLEAN NOT NULL DEFAULT TRUE,
    PRIMARY KEY (code),
    UNIQUE KEY uk_workflow_status_order (sort_order),
    CONSTRAINT chk_workflow_status_enabled CHECK (is_enabled IN (0, 1))
) ENGINE = InnoDB;

CREATE TABLE workflow_ticket (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    status_code VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    PRIMARY KEY (id),
    KEY idx_workflow_ticket_status (status_code),
    CONSTRAINT fk_workflow_ticket_status
        FOREIGN KEY (status_code) REFERENCES workflow_status (code)
) ENGINE = InnoDB;
```

父子列的类型、长度、字符集和 collation 应一致。字典表允许数据化管理状态, 但删除、禁用和缓存策略必须明确。

### 关联表替代 SET
成员需要属性、统计或权限完整性时, 使用多对多关联:

```sql
CREATE TABLE capability (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    code VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_capability_code (code)
) ENGINE = InnoDB;

CREATE TABLE integration_capability (
    integration_id BIGINT UNSIGNED NOT NULL,
    capability_id BIGINT UNSIGNED NOT NULL,
    granted_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (integration_id, capability_id),
    KEY idx_integration_capability_capability (capability_id),
    CONSTRAINT fk_integration_capability_capability
        FOREIGN KEY (capability_id) REFERENCES capability (id)
) ENGINE = InnoDB;
```

关联表占用更多行, 但能按成员索引、加外键、记录授予时间并做增量审计, 通常更符合业务权限和标签模型。实际项目还应让 `integration_id` 引用对应的 integration 主表。

## 选型对照

| 需求 | 推荐方案 |
| :--- | :--- |
| 很少变化的单选机器状态 | `ENUM`, 或 `VARCHAR + CHECK` |
| 可配置且有展示属性的单选状态 | 字典表 + 外键 |
| 很少变化的紧凑协议标志 | `SET` 或 `BIT` 位掩码 |
| 用户标签、角色权限、动态能力集合 | 成员表 + 关联表 |
| 需要跨数据库移植 | `VARCHAR + CHECK` 或关系表 |
