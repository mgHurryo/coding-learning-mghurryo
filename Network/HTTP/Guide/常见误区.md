# 常见误区

## 1. 把 GET 当 POST 用

❌ 错误：`GET /login?username=admin&password=123456`

✅ 正确：使用 POST，并通过请求体 + HTTPS 传输。

**原因**：
- 密码会暴露在 URL、浏览器历史、服务器日志中。
- GET 请求会被浏览器预加载、缓存，增加泄露风险。

## 2. 在 GET 请求中执行写操作

❌ 错误：`GET /deleteUser?id=123`

✅ 正确：`DELETE /users/123`

**原因**：
- 搜索引擎爬虫可能意外触发删除。
- 浏览器预加载可能导致误操作。
- 违反 HTTP 语义。

## 3. 用 POST 做所有操作

❌ 错误：所有接口都用 POST，URL 里全是动词。

✅ 正确：根据语义选择 GET/POST/PUT/PATCH/DELETE。

**原因**：
- 失去了 RESTful 设计的简洁性。
- 缓存、幂等性等优势无法发挥。

## 4. 忽视 URL 长度限制

❌ 错误：GET 请求携带大量参数或复杂查询条件。

✅ 正确：参数过多时改用 POST，或在服务端保存查询条件。

**原因**：
- 浏览器和服务器对 URL 长度有限制。
- 过长的 URL 不利于阅读和调试。

## 5. 混淆 401 和 403

| 场景 | 正确状态码 |
|------|-----------|
| 未登录或 Token 无效 | 401 |
| 已登录但无权限 | 403 |

## 6. 忽视 PUT 和 PATCH 的区别

- PUT：整体替换，未提供的字段可能被清空。
- PATCH：局部更新，只修改提供的字段。

## 7. 把 DELETE 设计成非幂等

❌ 错误：重复删除同一个资源返回 500。

✅ 正确：重复删除应返回 204 或 404，不产生新的副作用。

## 8. 在 GET 响应中返回敏感数据

GET 响应可能被 CDN、代理、浏览器缓存。涉及用户隐私的数据应谨慎设置缓存头，必要时使用 `Cache-Control: private, no-store`。

## 9. 返回不明确的状态码

- 创建成功 → 201
- 删除成功 → 204
- 参数错误 → 400
- 未认证 → 401
- 无权限 → 403
- 资源不存在 → 404

## 10. 忽略 CORS 预检

跨域接口使用自定义头或非简单方法时，服务端需要正确响应 OPTIONS 预检请求。
