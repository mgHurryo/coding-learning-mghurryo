# 11. 全局异常处理与统一响应

REST API 需要稳定的响应格式。全局异常处理可以把 Controller 或业务层抛出的异常集中转换为 JSON 响应，避免每个接口重复写 `try/catch`。

## 1. @RestControllerAdvice

`@RestControllerAdvice` 等价于 `@ControllerAdvice` 加 `@ResponseBody`，适合 REST API 场景。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        return Result.error("操作失败");
    }
}
```

## 2. @ExceptionHandler

`@ExceptionHandler` 声明某个方法处理指定异常。

异常匹配原则：

- 优先匹配更具体的异常类型。
- 没有具体处理器时，才走 `Exception.class` 兜底处理。

Big-event 中的 JWT 异常处理可以抽象为：

| 异常类型 | 响应含义 |
|----------|----------|
| Token 过期 | 要求重新登录 |
| Token 格式错误 | 请求认证信息无效 |
| Token 签名错误 | Token 可能被篡改 |
| 兜底异常 | 操作失败或服务器内部错误 |

## 3. 统一响应模型

统一响应通常包含：

| 字段 | 作用 |
|------|------|
| `code` | 业务状态码 |
| `message` | 可读提示 |
| `data` | 响应数据 |

注意区分：

- HTTP 状态码表达协议层结果。
- 业务 `code` 表达应用层结果。

## 4. 实战注意点

- 参数校验失败应该返回明确字段提示。
- 认证失败不要泄露密钥、签名细节和内部堆栈。
- 生产环境应使用日志框架记录异常，而不是只调用 `printStackTrace()`。
- 不要把数据库密码、JWT secret 等敏感配置写进错误响应。

## 5. Big-event 项目经验

Big-event 把接口返回统一封装为 `Result<T>`，并使用多个异常处理器处理 JWT 相关错误。长期维护时，可以考虑按异常领域合并处理器，减少重复类。
