# 认证安全与异常处理

## 1. 认证与授权

认证和授权是两个不同概念。

| 概念 | 解决的问题 | 例子 |
|------|------------|------|
| 认证 Authentication | 你是谁 | 用户名密码登录、Token 校验 |
| 授权 Authorization | 你能访问什么 | 普通用户、管理员、接口权限 |

在后端接口中，常见流程是：

1. 用户登录，服务端校验账号密码。
2. 校验成功后生成 Token。
3. 前端保存 Token。
4. 后续请求在请求头中携带 Token。
5. 服务端过滤器解析 Token，确认用户身份。
6. 认证通过后再访问 Controller。

## 2. Spring Security 过滤器链

Spring Security 的核心不是某一个 Controller，而是一组 Filter。

通用理解：

- 请求会先经过 Security Filter Chain。
- 过滤器可以在 Controller 之前完成认证、授权、拦截、放行。
- 自定义 JWT Filter 通常插入到 `UsernamePasswordAuthenticationFilter` 前面。

典型配置能力：

| 配置 | 作用 |
|------|------|
| `csrf().disable()` | JWT 前后端分离项目中常见配置 |
| `SessionCreationPolicy.STATELESS` | 服务端不保存 Session |
| `requestMatchers(...).permitAll()` | 配置登录、注册等白名单 |
| `anyRequest().authenticated()` | 其他接口必须认证 |
| `addFilterBefore(...)` | 把自定义过滤器加入过滤器链 |

通用注意点：

- 白名单接口必须覆盖登录、注册、错误页等无需登录的路径。
- 无状态认证意味着每次请求都必须携带 Token。
- Filter 中不要写复杂业务逻辑，只做认证相关判断。

## 3. JWT 基础

JWT 是一种自包含 Token，通常由三段组成：

```text
header.payload.signature
```

| 部分 | 作用 |
|------|------|
| Header | 说明 Token 类型和签名算法 |
| Payload | 保存用户标识、签发时间、过期时间等声明 |
| Signature | 用密钥签名，防止 Token 被篡改 |

通用认证流程：

1. 登录成功后生成 JWT。
2. Payload 中放入必要身份信息，例如用户 ID 或用户名。
3. 设置过期时间。
4. 使用服务端密钥签名。
5. 前端请求时放入 `Authorization` 请求头。
6. 服务端解析并校验签名和过期时间。

通用注意点：

- JWT Payload 默认只是 Base64Url 编码，不是加密，不要放密码、身份证号等敏感信息。
- 密钥必须足够长，并放在配置中管理。
- Token 一旦签发，在过期前通常无法天然失效，实际项目常配合黑名单、短期 access token 和 refresh token。

## 4. 无状态认证

无状态认证的意思是：服务端不保存用户会话。

优点：

- 更适合前后端分离。
- 服务端横向扩展更容易。
- 不依赖单机 Session。

代价：

- 每个请求都要带 Token。
- Token 泄露后，在过期前可能被滥用。
- 主动登出、踢人下线、权限实时变更需要额外设计。

## 5. 全局异常处理

`@RestControllerAdvice` 用于统一处理 Controller 层抛出的异常，并返回 JSON。

`@ExceptionHandler` 用于指定某个方法处理哪类异常。

通用结构：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        return Result.error("操作失败");
    }
}
```

异常匹配原则：

- 优先匹配更具体的异常类型。
- 没有具体处理器时，才走 `Exception.class` 兜底处理。

通用设计建议：

- 参数校验异常返回明确提示。
- Token 过期、格式错误、签名错误最好分别提示。
- 兜底异常不要把内部堆栈返回给前端。
- 生产环境应使用日志框架记录异常，而不是只调用 `printStackTrace()`。

## 6. 密码安全

MD5 是摘要算法，不适合现代密码存储。

MD5 的问题：

| 风险 | 说明 |
|------|------|
| 速度太快 | 容易被 GPU 暴力破解 |
| 无盐值时重复 | 相同密码生成相同哈希 |
| 彩虹表风险 | 常见密码可以被预计算反查 |
| 算法已过时 | 不推荐用于密码存储 |

更推荐使用 Spring Security 的 `PasswordEncoder`，例如 BCrypt：

```java
PasswordEncoder encoder = new BCryptPasswordEncoder();
String encoded = encoder.encode(rawPassword);
boolean matched = encoder.matches(rawPassword, encoded);
```

BCrypt 的优势：

- 自动加盐。
- 慢哈希，破解成本更高。
- 每次加密同一密码，结果也不同。
- 和 Spring Security 生态集成自然。

## 7. 安全实践清单

- 密码不要明文存储。
- Token 密钥不要写死在代码里。
- 接口默认需要认证，只对白名单放开。
- 统一异常响应，不泄露服务端内部细节。
- 登录失败、Token 失败等场景应有清晰但不过度暴露的信息。
- 涉及用户身份的操作，不要只信任前端传来的用户名，应优先从 Token 或服务端上下文获取身份。
